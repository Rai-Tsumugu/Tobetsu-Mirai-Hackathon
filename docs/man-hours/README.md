# 工賃見積もりに使う工数入力情報の体系化計画

- 作成日: 2026-10-11
- 状態: 提案・比較用ドラフト（採用案、補正値、実績データは未確定）
- 対象: 自動車整備工場で、作業に必要な人時を見積もり、工場の時間単価から工賃を決めるための入力情報
- ソース調査: [取得先・アクセス条件・確認記録](data-sources.md)（2026-10-11追記）

## 1. 目的と根拠

車両・作業・現車の状態・作業条件を同じ形式で記録し、「どの条件で工数が増えたか」を説明できるようにする。

[ヒアリング記録37](../hearing/新規録音%2037_文字起こし.txt)では、既存ソフトが型式と作業から時間を提示する一方、ネジの固着、付随作業、北海道での錆、雪下ろしによって時間が増えるという発言がある。また、過去見積もりはPC内にあるが、車両の状態は変化するという指摘がある。これはヒアリングでの発言であり、全車両への補正率や作業実績の計測結果ではない。

[既存要件定義](../app-demo/auto_repair_estimate_requirements.md)は、公開価格候補の比較を中心とし、標準作業時間・時間単価の導入時期を未確定としている。本計画はその検討資料として追加する。既存の価格比較方式を変更する決定ではない。

## 2. 3案の比較

| 案 | 工数の求め方 | 主な入力 | 着手に必要な情報 | 向いている場面 | 主な課題 |
|---|---|---|---|---|---|
| [A: 標準工数＋状態補正](plan-A.md) | 基準人時に、根拠のある追加工程・控除を加える | 適合車両、作業コード、基準人時、現車状態、追加工程 | 利用可能な基準人時と整備士が説明できる追加作業 | 既存ソフトの時間を起点に見積もる | 基準に含まれる工程と追加工程の重複を避ける必要がある |
| [B: 類似作業の実績参照](plan-B.md) | 条件の近い過去作業の人時と分布を参照する | 車両仕様、作業範囲、状態、実作業人時、類似条件 | 金額だけでなく人時が記録された実績 | 同種の整備を繰り返す工場 | 実績不足・条件の欠落・偏りがあると比較できない |
| [C: 工程ごとの積み上げ](plan-C.md) | 工程別の人数×実作業時間を合計する | 工程一覧、人数、時間、追加工程、共有工程 | 整備士が確認した工程テンプレート | 特殊作業や基準工数がない作業 | 入力負担が大きく、工程の漏れを防ぐ必要がある |

3案は同じ共通入力を使用する。案の選択と見積もりの確定は整備士・見積もり担当者が行う。異なる方法の推定値を無条件に平均しない。

## 3. 共通入力の辞書

「必須」は見積もり記録を作るための必須項目。「条件付き」は該当作業の工数に影響する場合に追加する項目。値が不明なこと自体は記録できるが、算出に必要な情報が欠ける場合は推定を止める。

| 区分 | 項目キー・入力情報 | 必須度 | 形式・単位 | 取得方法・目的 |
|---|---|---|---|---|
| 車両 | `vehicle`: メーカー、車種、型式、年式 | 必須 | 文字列、年 | 車検証・既存台帳等。適合する車両・作業候補を選ぶ |
| 車両仕様 | `vehicle_spec`: グレード、原動機、駆動方式、関連装備 | 条件付き | 選択値＋補足 | 現車・資料で確認。工数に影響する仕様だけ追加質問する |
| 作業範囲 | `job`: 作業コード、交換／修理／点検の別、部位、前後左右、数量 | 必須 | 選択値、個／組 | 整備士が指定。「ブレーキ」等の広い名称だけで確定しない |
| 含有工程 | `included_operations`: 脱着、診断、調整、確認等の含有範囲 | 必須 | 工程の一覧 | 使用する基準・事例・テンプレートの範囲を明示する |
| 現車状態 | `condition`: 錆、固着、損傷、改造、アクセスのしにくさ | 必須 | 状態別選択値＋観察メモ | 整備士が観察。未点検なら「不明」。年式から自動確定しない |
| 背景情報 | `usage_context`: 走行距離、使用地域、保管状況 | 任意 | km、地域、選択値 | 状態確認の補助情報。地域だけで工数を一律増加させない |
| 作業環境 | `work_context`: リフト、工具、作業スペース、車両の雪・氷 | 条件付き | 選択値＋補足 | 必要な設備の有無と、追加の準備作業を確認する |
| 同時作業 | `related_jobs`: 一緒に行う作業、共通の脱着・準備工程 | 条件付き | 作業・工程ID一覧 | 作業単位と見積もり全体の二重計上を避ける |
| 算出方法 | `method`: A／B／C、基準・事例・工程の参照ID | 必須 | 選択値、ID | どの方式とデータから見積もったかを追跡する |
| 根拠 | `evidence`: 情報源、確認日、観察者、対象仕様、データ版 | 必須 | 文字列、日付、ID | 現車確認・許可された資料・実績等の出所を保存する |
| 元データの単位 | `basis_value`、`basis_unit`: 原値と人時／時間／作業点数の別 | 算出時必須 | 数値、単位 | 提供元の定義を確認し、作業点数を人時として扱わない |
| 不確実性 | `unknowns`: 未確認項目、下限／上限の前提、追加確認事項 | 必須 | 一覧、自由記述 | 不足情報と見積もり条件を利用者に示す |
| 確定 | `approval`: 提案人時、確定人時、修正理由、確認者 | 確定時必須 | 人時、文字列 | 担当者が採用・修正した値と根拠を残す |
| 工賃換算 | `labor_rate`: 工場の時間単価、適用日 | 金額換算時必須 | 円／人時、日付 | 工場が設定した単価を使用する |

現車状態の暫定選択肢は「未確認／問題を観察していない／問題あり」とする。「問題あり」の詳細な段階や写真の判定基準は整備士への確認後に決める。「未確認」を「問題なし」に置き換えない。

各値には `value`（不明なら `null`）、`status`（確認済み／申告／仮定／不明）、`source`、`confirmed_at` を対応づける。仮定を使用した見積もりでは、その仮定を表示する。

## 4. 工数と金額の単位・計算規約案

- **人時**: 作業者ごとの実作業時間を合計する。2人が30分ずつ作業した場合は1.0人時。1人が30分作業した場合は0.5人時。
- **経過時間**: 作業開始から完了までの時間。並行作業や待機があるため、人時とは別に保持する。
- **待機時間**: 部品待ち、乾燥、連絡待ち等。作業者を拘束するかを確認し、実作業や工場の課金方針と区別する。
- **工賃換算案**: 確定した請求人時×工場の時間単価（円／人時）。実作業人時と請求人時が異なる場合は両方と理由を記録する。現在の工場の課金単位との対応は要確認。
- 部品代、材料費、税額は別項目。暖房費・家賃等を単価に含めるかは工場の価格方針として決め、根拠なく人時に足さない。
- 金額しかない公開料金・過去請求から、時間単価を推測して人時を逆算しない。人時の定義と単価が確認できた資料だけを工数の根拠候補にする。
- 保存する人時は丸める前の値とし、表示・請求時の丸め方は工場に確認する。

### ソース調査で確認した単位の区別

日整連の[公開説明](https://faines.jaspa.or.jp/enduser/system/files/static/score/score_manual.html)では、標準作業点数は標準作業時間に換算係数を乗じて設定される。定期点検では作業時間と点数を同じとしているが、一般整備の点数をそのまま実作業人時へ変換しない。

基準データは原値・単位・定義・適用版を保持する。点数しか得られない場合、Aの基準人時は未取得のままとし、時間データの確認またはCへ進む。円／点による工賃算定を採用する場合は、円／人時と別の計算方式として工場に確認する。取得先の詳細は[ソース調査](data-sources.md)のMH01〜MH04を参照する。

## 5. 進め方と成果物

| 段階 | 実施内容 | 成果物・完了条件 |
|---|---|---|
| 1. 業務確認 | 整備士と対象作業を1つ選び、基準時間の定義、含有工程、課金単位、状態の確認方法を聞く | 対象作業・必須項目・未確定事項の一覧ができる |
| 2. データ棚卸し | 既存ソフト、過去見積もり、作業実績にある項目を確認する | 利用可能／提供待ち／取得不可と利用範囲を記録する。過去見積もりに実時間があると仮定しない |
| 3. 共通入力の試作 | 共通辞書から車両→作業→状態→不足確認→人時・単価の順に入力票を作る | 必須・条件付き・任意と「不明」を選べる紙または画面の入力票 |
| 4. 3案の比較 | 同じ作業条件をA・B・Cに入力し、利用可能な根拠と不足を整理する | 各案の入力負担、根拠、算出可否、追加確認が比較できる |
| 5. 採用判断 | 整備士が説明しやすさと入力負担を評価する | 採用案・例外時の方式・次に収集する実績項目を決める |
| 6. 実績収集・見直し | 実作業人時、追加工程、見積もり時に不明だった条件を記録する | 見積もりとの差と原因を残し、辞書・補正・工程の見直しに使う |

着手案はAとする。ただし、適合する基準人時と利用可能な根拠があることが条件。基準がなければCの工程整理から始め、人時付きの実績が蓄積した段階でBを比較する。この順序は提案であり、採用決定ではない。

## 6. 計画実施時の確認項目

- 同じ型式でも年式・仕様が異なると、追加確認へ進めるか。
- 錆・固着が「未確認」のとき、0人時の補正として確定しないか。
- 車種と作業は同じでも、診断・調整等の含有範囲が異なる資料を区別できるか。
- 雪下ろし・共通脱着を複数作業で二重計上しないか。
- 2人作業の人時、経過時間、部品待ちを分けて記録できるか。
- 金額のみの実績は、工数算出の根拠不足として扱えるか。
- 根拠がない場合に数値を生成せず、担当者確認または手動見積もりに進めるか。

これらは今後の確認項目。アプリ実装、実車検証、補正値の妥当性検証は未実施。

## 7. 未確定事項

1. 工場が使う基準時間の定義・収録範囲・利用可能な形式。
2. 現車確認を誰が、どのタイミングで行うか。
3. 過去記録に実作業人時・人数・追加工程が残っているか。
4. 見積もり段階で確認できない固着・損傷への扱い。
5. 診断、試運転、雪下ろし等を作業別または見積もり全体のどちらで扱うか。
6. 実作業人時と請求人時の対応、時間単価、端数処理。
7. 状態分類、補正範囲、類似条件の採用基準を誰が承認・更新するか。
