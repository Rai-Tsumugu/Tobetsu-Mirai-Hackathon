# 工数見積もりの入力情報：取得ソース調査

- 確認日: 2026-10-11
- 対象: [共通入力辞書](README.md)、[案A](plan-A.md)、[案B](plan-B.md)、[案C](plan-C.md)
- 確認範囲: 提供元の公開ページ・仕様書・一部サンプル、公開APIの少量取得。契約者向けデータ、工場の実データ、アプリへの取込は未確認。

## 1. 調査結果と取得の優先順位

1. **車両情報**は、電子車検証の公式JSON／CSV出力とメーカー諸元資料が取得候補。電子車検証の公式サンプルは取得済みで、入力設計に使える（MH05・MH07）。
2. **Aの基準**は、日整連の標準作業点数表、FAINES、工場の既存見積もりソフトが候補。ただし、作業点数と実作業人時を分ける必要がある（MH01〜MH04）。
3. **Bの実績**は、工場の作業記録と今後の計測が主な取得先。公開整備事例は条件・作業範囲の参考になるが、「作業時間」をそのまま人時にできない（MH09・MH11・MH12）。
4. **Cの工程**は、適合する整備マニュアルと整備士への確認から作る。工程別の人時は現場で取得する（MH03・MH10・MH12）。
5. 国内仕様の車両別・作業別の信頼できる人時を、無料で網羅取得できる公開APIは今回の調査範囲では確認できなかった。海外APIにも候補はあるが、国内仕様への適合とデータの出所を確認してから評価する（MH13・MH14）。

### MH05の実取得結果と取込時の注意

国土交通省が公開する[登録車サンプルJSON](https://www.denshishakensho-portal.mlit.go.jp/assets/files/sample01.json)と[軽自動車サンプルJSON](https://www.denshishakensho-portal.mlit.go.jp/assets/files/K_sample01.json)をそれぞれHTTP 200で取得し、JSONとして読み取れることを確認した。これらは公式の形式例であり、今回の対象工場やFL4の実データではない。

| 入力項目 | 確認したキー／変換上の注意 |
|---|---|
| 型式・原動機型式 | `CertInfo.Model`、`CertInfo.EngineModel`。全角表記を正規化し、原値も保持する |
| 型式指定番号・類別区分番号 | `ModelSpecifyNo`、`ClassifyAroundNo`。先頭0を保持するため文字列として扱う |
| 初度登録／初度検査年月 | 登録車は`Firstregistdate*`、軽自動車は`Firstexamdate*`。元号と年月の別キーを使い、年月の意味を保持する |
| 寸法 | `Length`、`Width`、`Height`。別紙XLSXでcmと確認。共通マスターのmmへは数値化後に10倍する |
| 車名 | `CarName`。サンプルではメーカー名が入り、販売車種名まで得られるとは扱わない |
| 欠損 | 仕様書では文字列・空文字による出力が規定されている。空文字・項目固有の記号を辞書に従って不明へ変換する |

取込案は、必要な車両項目を抽出して共通辞書へ変換する。所有者名、住所、登録番号、完全な車台番号を工数入力の必須情報にしない。今回は公開サンプルと仕様を確認した段階で、実車の読取・CSV出力操作・アプリへの取込は未実施。

## 6. 次に行う取得手順

1. **公開サンプルで車両入力を設計**：MH05の必要キー・単位・登録車／軽自動車の差を入力辞書へ対応づける。公開サンプルの顧客欄はデモへ持ち込まない。
2. **工場の既存ソフトを確認**：製品名、加入サービス、1作業分の表示値・単位・含有範囲、必要項目の提供可能な形式を確認する。
3. **Aの取得可否を判断**：人時が得られるか、点数だけかを確認する。点数だけなら原値を保存し、人時の自動算出を保留する。外部アプリへの利用条件も確認する。
4. **B・C用に1作業を計測**：作業範囲、車両仕様、観察した状態、作業者別実時間、追加工程、待機を記録する。これは計測票の導入確認であり、1件で精度を認定しない。
5. **契約データの導入判断**：既存契約で足りない項目だけをFAINES・点数表・ベンダーへ確認する。料金・資格・利用範囲が確認できた段階で契約・申請を別途判断する。
