# 工数見積もりアルゴリズム：30案の比較と統合版の特徴

- 作成日: 2026-10-11
- 状態: 架空値による試作。補正値、実績データ、各種しきい値は未確定で、整備士との確認前
- 関連: [システム案30件](system-ideas-30.md)、[体系化計画・入力辞書](README.md)、[統合版の説明](../../src/30-algorithm/integrated/README.md)

## 1. 何を作ったか

[システム案30件](system-ideas-30.md)は、工数見積もりの仕組みを文章で並べたものである。
文章のままでは、どの案がどれだけ工数を動かすのかを比べられない。
そこで、各案を実際に計算できるアルゴリズムにし、同じ入力で計算して比べた。
さらに、比較で見えた各案の長所を一つの見積もりエンジンにまとめた。

成果物は次の二つである。統合版は `src/30-algorithm/integrated/` に置いている。30案のアルゴリズムと比較表は、統合版の元になった作業用の成果物として、別ブランチ `feat/30-algorithms` の `src/30-algorithm/` に置いている。

- **30案の演算アルゴリズムと比較表**：S01〜S30 を1案1本の Python スクリプトにし、同じ架空の入力で計算した結果を、入力内容、重要な途中計算、最終的な工数の表にまとめた
- **統合版の見積もりエンジン**：30案の長所を一つの処理の流れに組み込んだ決定版。過去の実績や最新の情報で変わる値をすべて変数ファイルに出し、コードに数値を残さない

数値はすべて架空値であり、補正率や人時の実測ではない。
計算結果は提案であり、確定は整備士と見積もり担当者が行う。

## 2. 30案の比較

### 同じ入力で比べる

比較では、全案が一つの共通シナリオを入力にする。
車両は初度登録から13年、走行12.8万kmの4WD SUV で、冬に入庫し、冬タイヤ交換とフロントブレーキのパッドとローターの交換を行う。
入庫時には車体に積雪があり、ブレーキ周りは錆が重度で、ボルトの一部とローターの固着は分解前のため未確認である。

各案は、重複を除いた基準工数 1.7 人時を出発点にし、その案が扱う要因だけを反映する。
このため最終工数の差は、その案が何を見ているかの差として読める。
各案の値を合算したり平均したりはしない。

### 解釈の統一

最初に実装した30案を検証し直したところ、合格は8案にとどまった。
残りの指摘の大半は計算の誤りではなく、案ごとにルールの読み方が割れていたことによる。
たとえば「未確認の項目は上限に入れる」と「他の案の要因を混ぜない」がぶつかり、ある案は上限に入れ、別の案は入れなかった。
これでは比較の前提がそろわない。

そこで、どの案にも同じ読み方をさせる9項目の解釈（U1〜U9）を共通仕様に定めた。
主な内容は次のとおりである。

- **上限（high）の意味**：その案が扱う範囲での上限とし、範囲内の未確認項目の上限を含める
- **締結部の割り当て**：錆「中」のボルトは標準値に固着対応を入れる。錆「重」のボルトは折れ込みとねじ山修正を上限にだけ入れる。分解前で見えないボルトは固着対応を上限にだけ入れる
- **作業範囲外の部位**：今回の作業で外さないサブフレームは上限にも入れず、腐食があれば見積もりを変更すると記録する
- **待機と人時の区別**：融解待ち、浸透待ち、防錆の乾燥待ちは経過時間にだけ入れる

### 3重チェック

各案は、Sonnet が実装し、Haiku 3体が独立に検証するチームで作った。
3体はそれぞれ、算術の再計算（実装を読まずに入力から計算し直す）、仕様と解釈の統一への適合、入力の整合と再現性を確かめる。
最終的に、16案が3体すべての判定に合格した。
9案は、Haiku の指摘がオーケストレーターの個別の指示と食い違ったため、指示どおりの実装を残して「裁定済み」とした。
3案（S07、S17、S29）は、工数の値に影響しない不足が残る「要確認」である。
残る2案（S12、S28）は、3重チェックのあとに経過時間を直したため、3体で再検証した。
S12 は案の範囲の定義が一貫しておらず（実績タグのない工程のうち、ねじ山修正だけを入れていた）、S28 は待機を扱うのに経過時間を出していなかった。
どちらも指摘に合わせて直し、S12 の工数は 2.35 / 3.16 / 10.45 人時になった。

### 比較から分かったこと

標準値（typical）は 1.70〜3.16 人時に収まった。
一方、上限（high）は 1.70〜11.35 人時まで開いた。
上限を大きく広げているのは、錆「重」のボルト2本が折れた場合の抜き取りとねじ山修正（＋4.0 人時）と、分解前で見えない部位（＋2.2 人時）である。
過去の類似実績を参照する案（S08）は上限が 3.0 人時で、工程を積み上げる案（8〜11 人時）より大幅に狭い。
これは参照した同じ作業の実績4件に折れ込みの例がないためで、どちらの幅が実態に近いかは、実績が溜まるまで判断できない。

確認優先度のスコアで上限の幅を切り替える案（S21）では、経過年数と走行距離の点数で帯が上がり、上限が 3.9 人時から 8.5 人時に動いた。
文書上は「年式から工数を増やさない」というガードレールを守っていても、スコアを経由すると年式が上限を動かせてしまう。
この問題は、統合版の設計判断に反映した（4章「30案から統合するときに決めたこと」）。

## 3. 統合版の値の分け方

### 変わる値と変わらない値

統合版は、見積もりに使う値を「変わる値」と「定義で決まる値」に分け、前者をすべて変数ファイルに出している。
変わる値をコードに書くと、実績が増えるたび、経費や材料の値段が変わるたびにコードを直すことになるからだ。
変数ファイルに出しておけば、更新はファイルの書き換えで済み、どの値で計算したかも記録に残る。

| 種類 | 置き場所 | 中身 | 変わるきっかけ |
|---|---|---|---|
| 過去の実績 | `data/records.json` | 見積もりと実作業人時、原因タグ、工程ログ、同一車両の履歴、他工場の匿名実績 | 作業が終わるたびに増える |
| 最新の情報と工場方針 | `data/shop_params.json` | 整備士の暫定値と請求の有無、状態に応じた工程の展開規則、しきい値、待機時間、加点表、経費、材料単価、丸め方 | 整備士の見直し、経費や材料の値上がり、方針の変更 |
| 基準工数 | `data/job_catalog.json` | 作業ごとの基準人時、含まれる工程、作業部位 | 基準データの版の更新 |
| 今回の入力 | `data/case_example.json` | 電子車検証、入庫時の観察、写真、気象予報、音声メモ | 見積もりごと |
| 定数 | `constants.py` | 和暦の元年、1年=12か月、状態の選択肢の名前など | 定義なので変わらない |

### マジックナンバーを残さない仕組み

見積もり本体のコードには、数値リテラルが一つもない。
数値は、変数ファイルの値か、名前を付けた定数のどちらかから来る。
この状態はテストで機械的に確かめている。
テストはコードの構文木を走査し、数値リテラルと、数値だけを表す文字列（"0.5" など）を探す。
今後だれかが数値を直書きすれば、テストが失敗する。

定数と変数の境目は、「実績や最新の情報で変わりうるか」で決めた。
和暦の元年（令和は2019年）や1年の月数は定義で決まるので定数にした。
冬季の月、タイヤを1人で扱える重量、円の丸め方は、工場の判断や観測で変わりうるので変数にした。
現車状態の選択肢の名前（「問題あり」など）も、[体系化計画](README.md) §3 では暫定とされているので変数に置き、コードは名前ではなく内部の ID で分岐する。
丸め方を変数にしたのは、[体系化計画](README.md) §4 で「工場に確認する」とされている事項だからで、Python 標準の丸めのままでは 1868.5 円が 1868 円になっていた。

読み込み時には、変数どうしの整合も検査する。
展開規則の種類や実績タグの単位を書き間違えると、エラーにならず別の扱いで計算が進むおそれがあるからだ。
状態の ID、展開規則の種類、実績タグの単位、補正表の版名、比較条件が既知の値であること、規則やタグが指す工程が暫定値にあること、暖房費が単価の経費に含まれていること、冬季と冬季以外の請求人時の合計が年間と一致することを確かめ、合わなければ計算を止める。

### 実績で育つ単価

工程ごとの単価（1本、1か所あたりの人時）は、整備士の暫定値（v1）から始まる。
エンジンは計算のたびに、実績の原因タグから1単位あたりの人時を集め、件数が最小件数（今回は3件）以上の工程だけ、次の版の候補（v2）を作る。
候補の作り方（最小値、中央値、最大値のどれを使うか）も変数ファイルに書いてある。

候補は自動では使わない。
整備士が候補を確認して承認したら、変数ファイルの採用版を v2 に書き換える。
実績の少ないうちに偏った値が見積もりに入るのを防ぎつつ、実績が溜まるほど自工場の実態に近づく。

## 4. 統合版の見積もりの出し方

### 処理の流れと取り込んだ案

| 段階 | 内容 | 取り込んだ案 |
|---|---|---|
| 車両情報 | 電子車検証の和暦を西暦に直し、初度登録からの経過年数と季節を出す。使用者の情報は取り込まない | S26 |
| 基準工数 | 選んだ作業の基準人時を合計し、共通工程を1回分にする。雪下ろしなどの前処理は入庫1回だけ計上する | S17 |
| 工程の展開 | 入庫時の状態に応じて工程を足す。締結部は1本ずつ錆の区分で扱い、タイヤ重量で運搬の人数を変える | S01、S02、S03、S05、S07、S15、S22 |
| 単価 | 承認済みの版を使い、実績から次の版の候補を作る。他工場の値は参照幅としてだけ示す | S11、S12、S13 |
| 3点見積もり | 少ない場合、観察から見込む値、上限の3つを出し、待機は経過時間にだけ足す | S18、S19 |
| 方式の比較 | 工程の積み上げと類似実績を並べ、平均しない | S08、S30 |
| 確認 | 確認強度、気象による前処理の確認、未確認項目の確認リスト、確認優先度、撮影の漏れ、AI と整備士の判定の一致、同一車両の前回との差 | S04、S06、S09、S16、S21、S23、S24 |
| 金額と説明 | 発生した場合だけの追加と作業前連絡の要否、時間単価、材料費の別建て、顧客向けの内訳 | S20、S27、S28、S29 |
| 記録の分析 | 見積もりと実績の差、工程ログの集計、音声メモの原因タグ振り分け | S10、S14、S25 |

### 3つの値と3つの時間

工数は、low、typical、high の3つの値で出す。

- **low**：観察で問題があった項目が、少ない手間で済んだ場合
- **typical**：観察済みの状態から見込む値
- **high**：見積もりの範囲での上限。未確認の項目と、錆「重」のボルトの折れ込みを含む

時間の面でも3つを分けている。
**実作業人時**は作業者が手を動かした時間の合計で、**請求人時**はそこから請求しない工程（下回り洗浄）を除いたもの、**経過時間**は待機を含む納車までの時間である。
工賃は請求人時に時間単価を掛けて出し、暖房費は人時ではなく時間単価の側で扱う。

### 発生した場合だけの追加

上限と標準値の差のうち、標準値に入っていない工程が上限で加わるもの（未確認の項目や折れ込み）は、「発生した場合だけの追加」として見積書に別記する。
工場の連絡基準（0.5 人時または 5,000 円）を超える追加は、作業前に顧客へ連絡する対象として示す。
初めから多めに見積もるのではなく、条件と上限を明示することで、追加作業の持ち出しを減らす狙いがある。

### 30案から統合するときに決めたこと

- **確認優先度で人時の幅を変えない**：2章で見たとおり、スコアを経由すると年式が上限を動かせてしまう。統合版では未確認と折れ込みを常に上限に入れ、スコアは確認の順番と時期にだけ使う
- **分析系の案は見積もりに直接足さない**：差分ログ（S10）を区分ごとに足すと、季節や年式による一律の加算になる。音声メモ（S25）と他工場の実績（S13）は確認前の候補である。いずれも、単価の候補を通して承認後に反映する
- **同一車両の前回実績は類似実績の集計から外す**：車の状態が前回から変わっているためで、前回実績は別の行として示す
- **AI の判定は計算に使わない**：整備士の確定値だけを使い、AI との一致率を表示する
- **重量が仮定値のタイヤは、2人作業の差分を標準値と上限にだけ入れる**：重量が確認できれば下限にも入る

## 5. 例の結果

共通シナリオ（架空値）で統合版を実行した結果は次のとおりである。

| 区分 | low | typical | high |
|---|---|---|---|
| 実作業人時（基準と状態に応じた工程の積み上げ） | 2.35 | 3.24 | 10.53 |
| 請求人時（請求しない下回り洗浄を除く） | 2.20 | 3.04 | 10.23 |
| 経過時間（待機 1.05 時間を含む） | 3.40 | 4.27 | 11.56 |
| 類似実績（3件。同一車両の前回は別に表示） | 2.30 | 2.40 | 3.00 |
| 工賃（請求人時 × 8,000 円） | 17,600 円 | 24,320 円 | 81,840 円 |
| 材料費（工賃と別） | 1,869 円 | 2,125 円 | 9,137 円 |

標準値の 3.24 人時は、30案の最大（3.16 人時）と同程度である。
30案がそれぞれ別々に見ていた要因（前処理、固着、ハブの錆、ブーツ、タイヤ重量）を、重複させずに足し合わせた値になっている。
上限との差 7.29 人時のうち 6.5 人時が発生した場合だけの追加で、そのうち 6.3 人時（折れ込み 4.3、見えないボルト 1.2、ローター固着 0.8）が作業前の連絡対象になる。

## 6. 検証の状況

統合版は、Haiku による独立検証を5回受けた。
1回目と2回目（修正後の版）は3体で、変数とマジックナンバーの監査、変数ファイルからの算術の再計算、ガードレールと30案の取り込みを見た。
3回目から5回目は、直前の修正点を1体が入力やデータを書き換えて再現し、確かめた。
算術はどの回でも全項目が一致し、30案のうち取り込まれていない案はなかった。

指摘の多くは、計算の誤りではなく、書き間違いや想定外の値が黙って別の扱いになる経路だった。
たとえば実績タグの数え方を取り違えると、エラーにならないまま単価の候補が倍になる。
これらを読み込み時の検査でエラーにし、請求しない工程を工賃と追加金額から除く修正などとあわせて、テスト（53件）で固定した。
5回目の指摘への修正（部位名と錆グレードの範囲、値の型、空の作業、規則を外したときの記録）は、テストで確認したが、独立検証にはかけていない。

検査しないと決めたものもある。
締結部の本数には上限を設けていない。
ホイールナットの20本のように正しい本数がデータからは決められず、上限を置くと正しい入力を弾くおそれがあるためだ。

## 7. 限界と未確定事項

数値はすべて架空値である。
整備士の暫定値、状態に応じた工程の展開規則、締結部の割り当て、しきい値、加点表は、整備士と工場に確認してから変数ファイルを書き換える。
コードの変更は要らない。

[システム案30件](system-ideas-30.md) §7 の未確定事項に加えて、次を確認する。

1. ハブ当たり面の錆落としと、基準のパッド交換に含まれる「清掃」が重なっていないか。
2. 2人作業で運搬の経過時間が短くなる扱い（2人が同時に運ぶ前提）が、現場の作業に合っているか。
3. 類似実績と工程の積み上げで上限の幅が大きく違う（3.0 人時と 10.53 人時）。どちらを見積書の上限として示すか。
4. 単価の候補（v2）を承認する手順と、承認する人。
5. 統合版では、現車状態の選択肢に、[体系化計画](README.md) §3 の3つ（問題あり、問題を観察していない、未確認）に加えて「仮定」（資料値の確認がない重量など）を使っている。§3 に追記するかを決める。
