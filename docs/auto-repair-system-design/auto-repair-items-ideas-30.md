# 役割
あなたは、小規模な自動車整備工場向け業務アプリの設計者です。ハッカソン当日に実装できる範囲で、具体的な実装案を30件設計してください。

# 背景
- 当別町の中小企業DXハッカソン。テーマCは「北海道ならではの自動車修理の工賃を計算する」。
- 対象は家族経営の自動車整備工場。社長がほぼ1人で接客・見積もり・作業をこなしている。
- 現状、工賃は経験と直感で決めている。リース中の見積もりソフトが型式別の標準工数を出すが、北海道の塩カルによる錆、固着、付帯作業、雪下ろしで実際の時間は大きく延びる（1時間の作業が2時間30分になることもある）。
- 塗料やシンナーなどの材料費は社長の入社時から倍になったが、工賃には反映できていない。暖房費や人件費も上がっている。
- 電話で伝えた金額を忘れることがある。PCを使うのは1日1〜2時間（見積書・請求書の作成）で、スマホで選択肢をタップする程度の操作なら問題ない。
- ハッカソンの作業時間は約6時間。まず動くものを作り、そのあと改善する。

# MVPの全体像と、システム間の受け渡し
MVPは次の5システムで構成する。
「① 工数算出エンジン → ③ 時間単価 → ④ 金額計算・内訳表示 ← ⑤ 部品・材料単価マスタ → ⑪ 帳票生成」
受け渡しデータはこの形式に合わせる。フィールドを追加するときは理由を書く。
- ①の出力 `labor`: { person_hours: {low, typical, high}, elapsed_hours: {low, typical, high}, breakdown: [{operation, hours, reason, status}], unknowns: [] }
- ③の出力 `labor_rate`: { yen_per_person_hour, effective_from, basis: [{label, value, unit}] }
- ⑤の出力 `items`: [{ item_id, name, category(部品|塗料|溶剤|消耗品), unit, unit_price, price_type(仕入|販売), source, updated_at }]
- ④の出力 `quote`: { lines: [], subtotal, tax, total: {low, typical, high}, reasons: [], confirmed_by, override_reason }
- ⑪は `quote` を受け取り、見積書・請求書を出力する

# 守ること
1. 数値はすべて架空値として明記する。実測値や相場として書かない。
2. 地域・年式・走行距離だけを理由に一律の倍率をかけない。加算は観察した状態と追加工程に対応づける。
3. 未確認の項目を0として扱わず、幅（low/typical/high）か条件付きで示す。
4. 人時と経過時間を分ける。乾燥・融解・部品待ちなどの待機は経過時間にだけ入れる。
5. 暖房費・家賃・人件費は人時に足さず、時間単価の側で扱う。
6. AIや計算の結果は提案にとどめる。確定するのは人で、修正した場合は理由を残す。
7. 外部データの利用規約・契約条件が確認できていないものは「未確認」と書く。スクレイピングを前提にしない。
8. 顧客名や通話音声などの個人情報は最小限にする。
9. 既存資料（S01〜S30など）と同じ内容の案は、新規として数えず既存IDを示す。

# 30案の作り方
- 個別指示の「分類と件数」に従い、30案が偏らないようにする。
- 次のどれか1つ以上が他の案と違う場合だけ別案として数える：データの持ち方／計算方式／操作手順／技術構成／自動化の度合い。
- 常識から外れた案は3〜5件まで含めてよい。その場合は「挑戦案」と明記する。
- 各案に次の項目を書く。
  - ID・名称・一言でいうと
  - 解決する困りごと（録音番号と発言の要旨）
  - 利用者の操作（スマホでの手順とタップ数の目安）
  - 入力／処理（計算式または擬似コード）／出力（上の受け渡し形式に沿う）
  - データの持ち方（テーブル・JSONなどの構造）
  - 技術構成（既存要件定義の構成で当日に使える範囲）
  - 実装の目安（1人で何時間か）
  - 強み／弱み・リスク
  - 必要な外部データと入手可能性（公開／契約／工場提供／架空）

## 1. 前提の確認：根拠と不明点

### 根拠として読んだ資料

- 録音36: 社長が経験則で金額を決め、電話で伝えた金額を忘れることがあるという会話。スマホで候補を選ぶ操作なら扱えそうという話がある。
- 録音37: 部品価格も変化し、塗料・シンナーが入社時から倍になったという社長の発言。青と赤、メタリックを含む色、同じパールでも種類によって費用が違い、細かく調べないと損をすることがあるという説明がある。これらは発言の要旨であり、溶剤の値上がり幅、色別相場、現在価格、市場価格、倍率の根拠としては使わない。
- 録音38: ナフサ等の原料価格変化が材料価格に関係する可能性と、都度調べているという会話。指標連動による自動価格確定の根拠にはしない。
- 要件定義: Simulatorで一連の見積もりを行い、工賃・部品代・税額・合計と参照元を保存する。技術候補はReact + TypeScript + Tailwind CSS / FastAPI / SQLite。外部連携前でも動作する。
- docs/man-hours/README.md: 部品・材料費は工賃と別項目。単位・根拠が不明なら確定せず、見積もり時の根拠を残す。
- docs/man-hours/system-ideas-30.md: S28「錆対応の材料・消耗品の別建て」は既存案。本書では材料のマスタ登録・価格更新と④への数量付き受け渡しを設計し、S28自体を新案として再計上しない。
- docs/man-hours/data-sources.md: 工場内記録や仕入情報は工場提供候補だが、提供形式・利用範囲は未確認。公開情報の閲覧は再配布・アプリ組込みの許可を意味しない。既存見積もりソフト、FAINES、卸サイト等のAPI・CSV・転記許諾は未確認。

### 不明点

既存の部品・塗料ソフト名、工場が使う品番体系、取引先数、仕入単価・販売価格の決め方、掛率の適用範囲、税・送料・入数・容量の扱い、塗料の配合表と調色費、在庫連携の有無、単価の有効期限、実伝票の提供可否、個人情報の有無は未確認。OCR・PDF読取・卸連携の利用条件も未確認。材料ごとの価格・配合・使用量の実値は受け取っていない。

### 共通契約・安全規則

出力は全案で同じ items 形を保つ。category は「部品／塗料／溶剤／消耗品」のいずれか、price_type は「仕入／販売」のいずれか。

    items = [{
      item_id, name, category, unit, unit_price,
      price_type, source, updated_at
    }]

単価を保存した項目の内部管理には、item_id、名称、分類、基準単位、正規化価格、価格区分、出所、確認日、状態、作成者を持つ。必要に応じて仕入先ID、入数、原単位、税区分、価格版ID、有効期間、元ファイル参照を内部列として追加する。単位変換の追跡、取引条件、見積もり再現性に必要な場合だけ使い、連携契約の items に勝手な必須列を増やさない。

④へ渡す見積行には item_id、数量、単位、適用した単価、price_type、参照価格版、計算根拠を内部保存し、見積作成時点の unit_price をスナップショットする。後日のマスタ更新は過去見積を変更しない。販売価格には仕入掛率を二重に適用しない。品目の単位と数量単位が一致しない場合は変換根拠が確認できるまで計算を止める。必須単価が未確認・期限切れ・単位不明なら0円を入れず、見積もりを停止するか、社長が条件付き価格を入力・承認する。条件付きの場合も根拠と期限を表示する。

ナフサ・原油等の公開指標は背景確認用の参考情報に限り、個別品目の販売単価や見積価格へ自動反映しない。仕入先サイトは利用規約・契約・APIの確認前にスクレイピングしない。顧客名、電話、車台番号、伝票上の個人情報は取り込まず、必要最小限の品目・価格情報だけを保存する。数値例は架空。React + TypeScript + Tailwind CSS / FastAPI / SQLite / JSON Simulatorを基本候補とする。

## 3. 各案の詳細

以下のタップ数と実装時間は架空の設計目安。各案は基礎画面・共通保存層があるSimulator上の最小スライスであり、合算して6時間で完成する意味ではない。1案を選んでMVPに絞る。共通の項目出力と単価停止規則をすべてに適用する。

### M01 塗料コード正規化
- **根拠と既存案との差分**: 録音37で社長は「青は安いけど赤は高い」、メタリックを含む青や種類の違うパールでは値段が違うと説明した。色コードと仕上げ属性で品目を区別する操作自体は社長の発言ではなく、この差を取り違えないための設計提案。既存S-ID該当なし。S28は錆対応材料の別建てで、塗料コード体系は扱わない。
- **一言／根拠**: メーカー色コード、原表記、仕上げ（ソリッド／メタリック／パール等）を別属性で持つ。録音37で青・赤、メタリック、同じパールでも差があるとの発言があるが、色名だけで価格を決めない。
- **スマホ／入出力**: 「塗料」→コード・仕上げ検索→候補確認→原表記確認→保存（約5タップ）。入力は架空コード・名称・category=塗料・単位・仕入または販売価格・出所・確認日。出力は共通 items。正規化できないコードは未確定のまま保存保留。
- **データ／技術／時間**: paint_code(id, maker, raw_code, normalized_code, finish, item_id)。React選択、FastAPI検証、SQLite、JSON fixture。1.5h。
- **強み・リスク／データ**: 色と価格の紐付けを説明しやすい。コード体系・調色料金・利用許諾は工場提供待ち／未確認。デモは架空値。

### M02 容量・入数単位変換
- **根拠と既存案との差分**: 録音37で社長は塗料・シンナーなどの材料費が上がり、細かく調べないと損をすると述べた。包装単位換算は録音で語られておらず、入数と基準単位の取り違えを防ぐ設計提案。既存S-ID該当なし。S28は材料費の別建てで、容量・入数換算は定義しない。
- **一言／根拠**: 仕入包装と見積単位を、定義済み換算だけで基準単位へ変換する。録音37の材料費を正しく扱うための基盤で、実際の包装は未確認。
- **スマホ／入出力**: 品目選択→仕入包装入力→基準単位確認→換算確認→保存（約5タップ）。例（架空）: 4本入りを1箱価格で登録し、単価=箱価格÷4本。出力unitは「本」等に統一。
- **データ／技術／時間**: unit_conversion(item_id, source_unit, base_unit, factor, evidence)。正数・同一次元の換算だけ許可。React / FastAPI / SQLite。2h。
- **強み・リスク／データ**: 入数違いによる金額誤りを防ぐ。容器残量や重量換算は密度・実使用量が必要で自動変換しない。入数・容量は納品書または工場提供、デモは架空。

### M03 仕入・販売の二列価格
- **根拠と既存案との差分**: 録音37で社長は材料費が上昇しても受け取る金額に反映されず、工場負担が大きくなると述べた。仕入価格と販売価格を分けて持つ操作は録音にない設計提案で、発言から掛率や販売価格を推定しない。S28は材料を工賃と別建てにする既存案。本案はその材料価格を仕入／販売の別レコードにする差分。
- **一言／根拠**: 同一品目の仕入価格と販売価格を別レコード・別ラベルで管理する。録音37は費用転嫁の課題を語るが、適正掛率や販売方針は示していない。
- **スマホ／入出力**: 品目選択→「仕入／販売」タブ→値と出所確認→保存（約4タップ）。仕入の変更で販売値を書き換えず、共通 items のprice_typeを選んで返す。
- **データ／技術／時間**: item_price(item_id, price_type, amount, currency, valid_from, source)。price_type別一意キー。React / FastAPI / SQLite。1.5h。
- **強み・リスク／データ**: 仕入原価と見積価格の混同を防ぐ。販売価格がない時は販売見積を止め、仕入に自動掛率を掛けない。工場価格は工場提供待ち、デモは架空。

## 5. MVP推奨3案とシステム接続

6時間の共同MVPでは **M07 単品価格入力フォーム + M08 クイック価格変更 + M30 見積時価格スナップショット** を最小構成として提案する。M07で架空fixtureと手入力の品目を登録し、M08で更新履歴付き価格版を作り、M30で採用価格を見積時点に固定する。外部API・PDF/OCR・卸連携はなくても一連の操作をデモできる。これは提案であり採用決定ではない。

1. **① 工数算出エンジン**は、工程の材料候補が承認された場合にだけ item_id と必要数量を⑤へ渡す。S28の材料別建てを再利用し、新しい工数補正を作らない。
2. **③ 時間単価**は、労務単価だけを出す。⑤の材料単価を③の原価プールへ重ねて含めない。
3. **⑤ 部品・材料単価マスタ**は、採用したitem_id、unit、unit_price、price_type、source、updated_atを返す。数量・価格版・確認状態は内部参照として管理する。
4. **④ 金額計算**は、数量×単価を材料行として工賃と分ける。価格・単位が不明なら材料金額を0円にせず、見積合計を確定せず要確認／条件付き状態にする。販売価格に仕入掛率を再適用しない。
5. **⑪ 帳票生成**は④のquoteを受け、材料名・数量・単位・見積時点価格・価格区分・必要な条件説明を出す。顧客向けに仕入先機密や個人情報を含めない。過去見積はsnapshotから再現する。

デモ例（すべて架空）: ①から「防錆剤」候補と数量が確認付きで届き、⑤が同じ単位の価格版を返し、④が材料行と工賃行を分けて計算、⑪が見積書案を表示する。単価版を更新しても既存見積の合計は変化しない。OCR・PDF・Excel実装が6時間範囲を超える場合はmock読取結果または単品手入力へ戻し、存在しない外部取得や実データ連携を装わない。

## 6. 未確定事項と社長への確認質問

- 仕入単価と販売価格は現在どの資料・ソフトで確認し、どの値を見積へ使っているか。

- 塗料の色コード、配合、メタリック・パール等の仕上げはどの帳票・ソフトで管理しているか。アプリへの転記・保存は許されているか。
- 仕入先ごとに同じ品目の価格を比べる必要はあるか。通常価格・特価・有効期間をどう確認しているか。
- 「仕入」「販売」の2価格を記録するか。販売価格は品目ごとの手入力か、社長承認済み掛率を使うか。
- 価格の確認頻度と「古い」と判断する期間はどれくらいか。品目別に異なるか。
- 使用量を面積・色・工程から候補表示する必要はあるか。工場独自の配合・使用量記録があるか。
- 見積書に材料名・数量・単位・価格をどこまで表示するか。材料費と工賃の表示方法はどうするか。
- 過去見積もりや伝票を取り込む場合、個人情報を除去した見本を提供できるか。CSV／Excel／PDFのどれか。
- 仕入先サイト・カタログ・JSON等に外部連携契約があるか。利用規約、API、アプリ保存・再配布許諾は確認できるか。
- 単価や数量が未確認の時、見積を止めるか、期限付きの条件付き価格を人が入力するか。
- 端数処理、税区分、価格改定後の見積有効期限と過去見積保存年数はどうするか。
