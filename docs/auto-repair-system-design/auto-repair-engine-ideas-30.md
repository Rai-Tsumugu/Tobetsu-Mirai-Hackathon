# 役割
あなたは、小規模な自動車整備工場向け業務アプリの設計者です。ハッカソン当日に実装できる範囲で、具体的な実装案を30件設計してください。

# 背景
- 当別町の中小企業DXハッカソン。テーマCは「北海道ならではの自動車修理の工賃を計算する」。
- 対象は家族経営の自動車整備工場。社長がほぼ1人で接客・見積もり・作業をこなしている。
- 現状、工賃は経験と直感で決めている。リース中の見積もりソフトが型式別の標準工数を出すが、北海道の塩カルによる錆、固着、付帯作業、雪下ろしで実際の時間は大きく延びる（1時間の作業が2時間30分になることもある）。
- 塗料やシンナーなどの材料費は社長の入社時から倍になったが、工賃には反映できていない。暖房費や人件費も上がっている。
- 電話で伝えた金額を忘れることがある。PCを使うのは1日1〜2時間（見積書・請求書の作成）で、スマホで選択肢をタップする程度の操作なら問題ない。
- ハッカソンの作業時間は約6時間。まず動くものを作り、そのあと改善する。

# MVPの全体像と、システム間の受け渡し
MVPは次の5システムで構成する。
「① 工数算出エンジン → ③ 時間単価 → ④ 金額計算・内訳表示 ← ⑤ 部品・材料単価マスタ → ⑪ 帳票生成」
受け渡しデータはこの形式に合わせる。フィールドを追加するときは理由を書く。
- ①の出力 `labor`: { person_hours: {low, typical, high}, elapsed_hours: {low, typical, high}, breakdown: [{operation, hours, reason, status}], unknowns: [] }
- ③の出力 `labor_rate`: { yen_per_person_hour, effective_from, basis: [{label, value, unit}] }
- ⑤の出力 `items`: [{ item_id, name, category(部品|塗料|溶剤|消耗品), unit, unit_price, price_type(仕入|販売), source, updated_at }]
- ④の出力 `quote`: { lines: [], subtotal, tax, total: {low, typical, high}, reasons: [], confirmed_by, override_reason }
- ⑪は `quote` を受け取り、見積書・請求書を出力する

# 守ること
1. 数値はすべて架空値として明記する。実測値や相場として書かない。
2. 地域・年式・走行距離だけを理由に一律の倍率をかけない。加算は観察した状態と追加工程に対応づける。
3. 未確認の項目を0として扱わず、幅（low/typical/high）か条件付きで示す。
4. 人時と経過時間を分ける。乾燥・融解・部品待ちなどの待機は経過時間にだけ入れる。
5. 暖房費・家賃・人件費は人時に足さず、時間単価の側で扱う。
6. AIや計算の結果は提案にとどめる。確定するのは人で、修正した場合は理由を残す。
7. 外部データの利用規約・契約条件が確認できていないものは「未確認」と書く。スクレイピングを前提にしない。
8. 顧客名や通話音声などの個人情報は最小限にする。
9. 既存資料（S01〜S30など）と同じ内容の案は、新規として数えず既存IDを示す。

### 共通契約 C と停止規則

以下の数値例、実装時間、タップ数、評価点はすべて架空の設計想定。精度、実測工数、価格相場、確約ではない。ID番号や件数は仕様上の識別子である。

```typescript
type Range = { low: number|null; typical: number|null; high: number|null };
type Labor = {
  person_hours: Range; elapsed_hours: Range;
  breakdown: { operation: string; hours: Range; reason: string; status: string }[];
  unknowns: string[];
};
```

`breakdown.hours`をスカラーからRangeとして解釈する理由は未確認工程を典型値だけへ潰さないため。利用側④と実装前に型合意する。追加フィールドはlabor内に作らず内部envelope `{labor, engine_id, rule_version, trace, operation_keys, approvals}`に置く。版の再現、重複防止、確認履歴が理由であり③④⑤⑪の契約は変えない。statusは `proposed / confirmed-observation / conditional / missing-required / wait / nonbillable-work`。

必須の作業範囲、含有工程、基準単位、対象状態または承認済み条件幅が不足したら両Rangeの3値はnull、該当行もnull、statusはmissing-required、unknownsへ不足キーを返し④の金額算出を停止。単に未確認を0へ変換しない。計算に無関係な未確認部位はunknownsに残し関連性を理由に説明する。条件幅の使用は人の承認前提でconditionalのまま出す。

確認済み待機は行の人時Rangeを0にし、reasonへ経過時間の範囲と非拘束の根拠を記す。待機経過が不明ならelapsed_hoursはnull。人時=Σ人数×実作業時間、直列の経過=Σ工程所要時間+待機、並列は依存DAGのcritical path（作業者の資源競合も検証）。総人時を人数で割るだけで納期を出さない。洗浄は実施人時を残しnonbillable-work、④が承認された課金控除を別行で処理する。暖房・家賃・人件費は③、材料費は⑤で扱う。人が工数を修正すれば旧値・新値・理由・担当者をapprovalsへ保存する。

- **分類／一言**：実行環境／許諾済み基準を手で持ち込む。

## 5. MVPに推奨する3案と組み合わせ

推奨はE02（版付きJSON）＋E07（検証パイプライン）＋E13（スキーマ駆動状態フォーム）。E13で作業・対象状態・未確認を入力し、E02の承認版に格納したS01/S05/S19/S18をE07で評価する。架空の基準人時を手入力し、雪・氷・観察した固着対応を工程へ対応づけ、未確認固着は人が条件幅を承認するまで停止する。S18は最初は直列工程だけとし並列DAGはE09を後日に回す。共有工程があるfixtureの比較には控除済みフラグを必須とし、MVPデモの入力作業は一作業に絞る。

当日全体6時間に対し①の最小sliceを架空計画1.5時間（JSON/schema 0.4、フォーム0.4、計算0.4、契約と欠落確認0.3）に絞る。各案の単独実装目安の合計ではなく既存共通部品を再利用する別スコープの見積もり。残り4.5時間は③0.5、⑤0.5、④1.0、⑪0.75、横断統合とデモ1.75という架空予算案。すべて1人順次なら十分とは保証せず、チームが各領域を並行担当して契約テストを共有する。進捗に応じてフォーム入力項目と帳票装飾を減らす。

連携：①はlaborを④へ直接渡す。③は費用と請求可能時間からlabor_rateを独立計算して④へ渡し、①の待機や経費を人時へ足さない。⑤はitemsを④へ渡す。①の工程→材料候補は任意の内部mapで⑤の品目候補を参照するだけで、自動で部品購入や単価確定をしない。④は幅のまま人時×単価と材料行を作り、値の出所①③⑤を残す。非請求洗浄の控除や採用幅・最終価格の確定も④で人が行う。⑪は④のquoteから帳票化し、①のconditional/unknownsを④のreasons経由で引き継ぐ。①がmissing-requiredなら④・⑪は正式額の確定を止め、確認用の下書きのみとする。顧客・車両紐付けと電話伝達ログの責任は④であり①は匿名識別子だけでよい。

MVP受け入れ予定：同じJSON版と入力は同じlabor、未確認は0に変換されない、基準単位不明は停止、待機は人時に加算されない、2人作業を人数×所要時間で記録、修正理由が残る、再読込後もSQLiteのsnapshotを再表示。この文書でそれらの実装動作を検証したとは主張しない。
