あなたは、小規模な自動車整備工場向け業務アプリの設計者です。ハッカソン当日に実装できる範囲で、具体的な実装案を30件設計してください。

# 背景
- 当別町の中小企業DXハッカソン。テーマCは「北海道ならではの自動車修理の工賃を計算する」。
- 対象は家族経営の自動車整備工場。社長がほぼ1人で接客・見積もり・作業をこなしている。
- 現状、工賃は経験と直感で決めている。リース中の見積もりソフトが型式別の標準工数を出すが、北海道の塩カルによる錆、固着、付帯作業、雪下ろしで実際の時間は大きく延びる（1時間の作業が2時間30分になることもある）。

# MVPの全体像と、システム間の受け渡し
MVPは次の5システムで構成する。
「① 工数算出エンジン → ③ 時間単価 → ④ 金額計算・内訳表示 ← ⑤ 部品・材料単価マスタ → ⑪ 帳票生成」
受け渡しデータはこの形式に合わせる。フィールドを追加するときは理由を書く。
- ①の出力 `labor`: { person_hours: {low, typical, high}, elapsed_hours: {low, typical, high}, breakdown: [{operation, hours, reason, status}], unknowns: [] }
- ③の出力 `labor_rate`: { yen_per_person_hour, effective_from, basis: [{label, value, unit}] }
- ⑤の出力 `items`: [{ item_id, name, category(部品|塗料|溶剤|消耗品), unit, unit_price, price_type(仕入|販売), source, updated_at }]
- ④の出力 `quote`: { lines: [], subtotal, tax, total: {low, typical, high}, reasons: [], confirmed_by, override_reason }
- ⑪は `quote` を受け取り、見積書・請求書を出力する

# 守ること
1. 数値はすべて架空値として明記する。実測値や相場として書かない。
2. 地域・年式・走行距離だけを理由に一律の倍率をかけない。加算は観察した状態と追加工程に対応づける。
3. 未確認の項目を0として扱わず、幅（low/typical/high）か条件付きで示す。
4. 人時と経過時間を分ける。乾燥・融解・部品待ちなどの待機は経過時間にだけ入れる。
5. 暖房費・家賃・人件費は人時に足さず、時間単価の側で扱う。
6. AIや計算の結果は提案にとどめる。確定するのは人で、修正した場合は理由を残す。
7. 外部データの利用規約・契約条件が確認できていないものは「未確認」と書く。スクレイピングを前提にしない。
8. 顧客名や通話音声などの個人情報は最小限にする。
9. 既存資料（S01〜S30など）と同じ内容の案は、新規として数えず既存IDを示す。

## 1. 前提の確認：共通前提・根拠・不明点

### 共通前提は冒頭掲載

### 本書の範囲と計算規約

ここでいう時間単価は、工場が決める売上単価である `yen_per_person_hour`。工場の原価、期間の請求可能人時、目標利益などから候補を出す。期間能力の総労働人時 `H_period_total` と請求可能割合 `u_period` は別々に保持し、時間単価を算出する期間分母にだけ使う。個別案件の請求人時は、①の `person_hours` から工場が請求不可と承認した工程人時だけを除いた `H_job_billable` とする。

```text
H_period_bill = H_period_total × u_period

H_job_billable = H_job_from_① - Σ(工場が請求不可と承認した工程の人時)
labor_amount = H_job_billable × yen_per_person_hour
```

`u_period` は工場の期間実績または人が承認した計画値であり、期間分母 `H_period_bill` を作るための割合である。個別案件には掛けない。案件ごとの請求人時は、①の実作業人時 `H_job_from_①` から、工場が請求不可と承認した工程だけを差し引き、その工程名・人時・除外理由・承認者を記録して求める。`person_hours` のlow/typical/highの幅は維持し、除外人時も同じ条件の幅で扱う。不明工程を勝手に除外したり0と確定したりしない。

時間単価の費用プールは、円／人時へ配賦する費用（例: 家賃・暖房・設備等）と、別請求する材料・部品費を区別する。材料費を⑤で別計上する場合は③の費用プールから外し、二重算入を防ぐ。人件費は採用する原価方式に応じて一度だけ含める。家族労務は「実支払給与」と「仮の労務原価」を別項目にし、実支払がないことを労務価値ゼロとしない。

単価式の期間分母 `H_period_bill` が0、または未取得なら数値を確定しない。案件の必要な作業人時・請求不可工程が不明なら、案件金額の確定を停止するか、承認済み条件幅を示す。全案の数値例・タップ数・1人時間・評価点は架空の設計想定であり、実データや現場検証を示さない。

`labor_rate` は全案で次の形を維持する。追加の説明情報は `basis` の行に収め、外部契約の推測値を入れない。

```json
{
  "yen_per_person_hour": 6000,
  "effective_from": "2026-11-01",
  "basis": [
    {"label":"配賦費用合計（架空）", "value":7200000, "unit":"円/年"},
    {"label":"請求可能人時（架空）", "value":1200, "unit":"人時/年"}
  ]
}
```

## 3. 各案の詳細

### R01 年間原価積上げ単価（算定式）

- **一言**: 年間に配賦する工場費用を、年間の請求可能人時で割る基本式。S27の年間配賦を再利用する。新しい差分は総労働人時と請求可能割合 `u_period` を分け、ゼロ・不明の分母で確定を止めること。
- **困りごと・根拠**: 録音37で家賃・人件費が単価差になるという発言。録音37で暖房費の上昇も発言。実際の額は未提供。
- **スマホ手順**: 「費用入力」→年間費用合計→年間総労働人時→請求可能割合→「試算」→内容確認→社長承認（約7タップ）。
- **入力・計算・出力**: 入力 `annual_allocable_cost` 円、`H_period_total` 人時/年、`u_period`。式 `H_period_bill=H_period_total*u_period`; `rate=annual_allocable_cost/H_period_bill`。架空例で費用720万円、H_period_total=1,600、u_period=0.75なら6,000円/人時。いずれか不足・H_period_bill=0なら停止。出力は `labor_rate`。
- **データ**: `rate_period(id, from, to, H_period_total, u_period, H_period_bill, proposed_rate, status)`、`rate_cost(id, period_id, category, amount, included_in_rate, source_status)`。暖房、家賃、人件費を分け、⑤計上の材料費は `included_in_rate=false`。
- **技術**: React入力フォーム、FastAPIで計算、SQLite保存。年間費用は架空JSONでSimulator可。
- **実装時間**: 2.5h。**強み**: 式の根拠を説明しやすい。**弱み・リスク**: 費用範囲・`u_period`が誤ると単価も変わる。人件費を重ねて計上しない。
- **外部データ**: 工場提供（MH11相当、提供・CSV可否未確認）。公開の一般相場や無料単価APIは根拠として確認できていない。デモは架空。

### R02 粗利目標逆算単価（算定式）

- **一言**: 目標粗利率から必要な売上単価を逆算する。利益額の積上げとは異なる式。
- **困りごと・根拠**: 録音37で「やっても会社に利益が出ない」という趣旨の発言。粗利率の希望は未確認。
- **スマホ手順**: 原価候補を選ぶ→原価/人時確認→粗利率を入力→候補計算→説明表示→承認（約6タップ）。
- **入力・計算・出力**: 原価率 `c` 円/人時、粗利目標 `m` (0≤m<1)。`rate=c/(1-m)`。架空例: 原価4,800、粗利率20%なら6,000円/人時。利益率と原価への単純上乗せ率を混同しない。出力 `basis` にcとmを含む。
- **データ**: `margin_target(period_id, cost_per_hour, gross_margin, proposed_rate, status)`。
- **技術**: FastAPI数式検証とReactの%スライダー。Simulator用fixture。
- **実装時間**: 2h。**強み**: 目標率と式が明快。**弱み・リスク**: 「粗利」の定義、他費目をどこに含むかを経営者と合意する必要。
- **外部データ**: 工場提供の原価・目標率が必要。公開情報・契約データで当該工場の利益率は取れない。架空入力のみ。

## 5. MVP推奨3案と5システムの接続

### 推奨

1. **R15 金額だけの年次入力**：費用内訳が揃っていない初回でも、合計・分母・材料除外の確認を一画面で行える。ゼロや未入力のH_period_billでは停止する。
2. **R05 原価下限＋目標利益単価**：原価候補と利益目標を分けて見せる。短いデモでも単価の決まり方を説明でき、利益率方式と利益額方式を混同しない。
3. **R25 社長承認・履歴管理**：算定結果を自動確定せず、社長が確定した値と理由・適用日を記録する。電話で伝えた金額の記憶依存にもつながる。

### 6時間の切り出し想定と連携

MVPは上の3案を最小構成で組み合わせた約6時間の共同実装範囲。各案の個別実装見積を足した時間でも、残り27案の実装時間でもない。全費用値、単価、率、時間は画面に「架空デモ値」と表示する。

- **① 工数算出エンジン**: `person_hours` のlow/typical/highと内訳根拠を受ける。工場は①の内訳から請求不可と承認する工程だけを選び、工程・人時・理由・承認者を記録する。**③の `u_period` は期間分母専用で、案件には適用しない。**
- **③ 本書の出力**: 社長承認済み `labor_rate={yen_per_person_hour,effective_from,basis:[...]}` を発行する。不足分母・未承認値は数値確定しない。
- **④ 金額計算・内訳表示**: 案件の `H_job_billable=①の実作業人時-工場承認済みの請求不可工程人時` とし、除外工程・人時・理由・承認者を記録する。`labor_amount=H_job_billable*yen_per_person_hour` とする。`u_period` は案件の掛算に使わない。①のlow/typical/highと価格幅を保ち、請求不可工程も対応する条件幅から差し引く。労務行と材料行を分離する。既存F-05の候補中央値は別方式として残し、算出結果を混ぜない。
- **⑤ 部品・材料単価マスタ**: 個別に顧客へ請求する部品・塗料・溶剤・消耗品は⑤の `items` で扱い、③の原価プールには重ねて入れない。内部で原価配賦する材料は、見積で別建てするかどうかを人が指定する。
- **⑪ 帳票生成**: ④の確定 `quote` を受け取り、③の適用単価・有効日・内訳根拠を見積書へ必要な範囲で表示する。給与など非公開の内部情報は顧客向け帳票に含めない。

S27の年間/冬季配賦案はR08/R09/R28で既存案と明記して再利用し、請求可能割合・停止条件・顧客受容リスクの設計差を示した。S29は将来の説明帳票連携であり、R27〜R30を新規として設計する差分は原価内訳・季節差・現行単価差・根拠状態の画面表現である。既存S27を同内容のまま新案として数えていない。
