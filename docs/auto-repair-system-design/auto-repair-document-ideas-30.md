# 役割
あなたは、小規模な自動車整備工場向け業務アプリの設計者です。ハッカソン当日に実装できる範囲で、具体的な実装案を30件設計してください。

# 背景
- 当別町の中小企業DXハッカソン。テーマCは「北海道ならではの自動車修理の工賃を計算する」。
- 対象は家族経営の自動車整備工場。社長がほぼ1人で接客・見積もり・作業をこなしている。
- 現状、工賃は経験と直感で決めている。リース中の見積もりソフトが型式別の標準工数を出すが、北海道の塩カルによる錆、固着、付帯作業、雪下ろしで実際の時間は大きく延びる（1時間の作業が2時間30分になることもある）。
- 塗料やシンナーなどの材料費は社長の入社時から倍になったが、工賃には反映できていない。暖房費や人件費も上がっている。
- 電話で伝えた金額を忘れることがある。PCを使うのは1日1〜2時間（見積書・請求書の作成）で、スマホで選択肢をタップする程度の操作なら問題ない。
- ハッカソンの作業時間は約6時間。まず動くものを作り、そのあと改善する。

# MVPの全体像と、システム間の受け渡し
MVPは次の5システムで構成する。
「① 工数算出エンジン → ③ 時間単価 → ④ 金額計算・内訳表示 ← ⑤ 部品・材料単価マスタ → ⑪ 帳票生成」
受け渡しデータはこの形式に合わせる。フィールドを追加するときは理由を書く。
- ①の出力 `labor`: { person_hours: {low, typical, high}, elapsed_hours: {low, typical, high}, breakdown: [{operation, hours, reason, status}], unknowns: [] }
- ③の出力 `labor_rate`: { yen_per_person_hour, effective_from, basis: [{label, value, unit}] }
- ⑤の出力 `items`: [{ item_id, name, category(部品|塗料|溶剤|消耗品), unit, unit_price, price_type(仕入|販売), source, updated_at }]
- ④の出力 `quote`: { lines: [], subtotal, tax, total: {low, typical, high}, reasons: [], confirmed_by, override_reason }
- ⑪は `quote` を受け取り、見積書・請求書を出力する

# 守ること
1. 数値はすべて架空値として明記する。実測値や相場として書かない。
2. 地域・年式・走行距離だけを理由に一律の倍率をかけない。加算は観察した状態と追加工程に対応づける。
3. 未確認の項目を0として扱わず、幅（low/typical/high）か条件付きで示す。
4. 人時と経過時間を分ける。乾燥・融解・部品待ちなどの待機は経過時間にだけ入れる。
5. 暖房費・家賃・人件費は人時に足さず、時間単価の側で扱う。
6. AIや計算の結果は提案にとどめる。確定するのは人で、修正した場合は理由を残す。
7. 外部データの利用規約・契約条件が確認できていないものは「未確認」と書く。スクレイピングを前提にしない。
8. 顧客名や通話音声などの個人情報は最小限にする。
9. 既存資料（S01〜S30など）と同じ内容の案は、新規として数えず既存IDを示す。

# 30案の作り方
- 個別指示の「分類と件数」に従い、30案が偏らないようにする。
- 次のどれか1つ以上が他の案と違う場合だけ別案として数える：データの持ち方／計算方式／操作手順／技術構成／自動化の度合い。
- 常識から外れた案は3〜5件まで含めてよい。その場合は「挑戦案」と明記する。
- 各案に次の項目を書く。
  - ID・名称・一言でいうと
  - 解決する困りごと（録音番号と発言の要旨）
  - 利用者の操作（スマホでの手順とタップ数の目安）
  - 入力／処理（計算式または擬似コード）／出力（上の受け渡し形式に沿う）
  - データの持ち方（テーブル・JSONなどの構造）
  - 技術構成（既存要件定義の構成で当日に使える範囲）
  - 実装の目安（1人で何時間か）
  - 強み／弱み・リスク
  - 必要な外部データと入手可能性（公開／契約／工場提供／架空）

## 1. 前提の確認

参照資料：録音36・37・38、docs/app-demo/auto_repair_estimate_requirements.md、docs/man-hours/README.md、system-ideas-30.md、data-sources.md。録音36・37から、社長が接客・見積・作業をほぼ一人で担うこと、電話で伝えた額を忘れることがあること、スマホのタップ操作なら使えそうなこと、既存ソフトの標準時間だけでは錆・固着・付帯作業・雪下ろしを反映できないことを当事者発言として扱う。録音38は話者ラベルのない一続きの文字起こし。「最新版からすぐ金額」「紙にも出す」、FAINESや海外APIの話は参加者側の整理・提案として参照し、社長の直接要望と断定しない。

要件定義のReact + TypeScript + Tailwind CSS、FastAPI、SQLite、JSON、Simulatorを前提とし、外部接続なしで架空JSONの生成・保存・再表示をデモする。帳票・PDF・共有案は提案で実装済みではない。共有はpreview/mockで止め、実送信しない。顧客名・ナンバー・完全な車台番号等を保存せず匿名IDを使い、音声保存を前提にしない。既存S20（条件付き見積書）とS29（顧客向け説明シート）は内容を再掲するだけでは新案と数えない。生成構成・操作・状態・データ・接続の差を新案とする。

### 受け渡し契約
⑪は④のquote snapshotの保存値を表示する。⑪は金額を再計算・再丸め・変更しない。帳票前に明細の保存値と`subtotal`・`tax`・`total`の整合を検査し、不一致・必須値不足なら生成を止め、④で再計算して人が確定した新しい`quote_version`を受け取る。インボイスの税率ごと一回の端数処理は④がquoteを算出・保存するときに行い、⑪は保存済み税額を転記する。横断契約では①の実作業人時を保持し、④が承認済み非請求工程だけを除外してH_job_billable幅と単価から請求額を作る。⑪は除外済み工程を復活させず、非請求理由・承認者由来のquote理由を保持する。現行要件はsubtotal/taxがscalarでtotalのみ幅だが、scalarでは幅が消えるため下記のようにsubtotal/taxも明示的にMoneyRangeにする差分提案。④との契約合意が必要。

    type MoneyRange = { low: number|null; typical: number|null; high: number|null };
    type Quote = {
      lines: { label: string; quantity: number|null; unit: string|null;
        amount: MoneyRange; tax_category: string|null; source_ids: string[] }[];
      subtotal: MoneyRange; tax: MoneyRange; total: MoneyRange;
      reasons: string[]; confirmed_by: string|null; override_reason: string|null;
    };
    type ApprovalSnapshot = {
      quote_version: string;
      confirmed_amount: {
        subtotal: number|null; tax: number|null; total: number|null;
        selection: "low"|"typical"|"high"|"override"|null;
      };
      confirmed_by: string|null; confirmed_at: string|null;
      override_reason: string|null;
      condition_acceptance: { condition_id: string; status: "accepted"|"declined"|"pending";
        confirmed_by: string|null; confirmed_at: string|null; reason: string|null }[];
    };
    type DocumentEnvelope = { quote: Quote; approval_snapshot: ApprovalSnapshot|null };

`approval_snapshot`は概算幅を変更せず保持したまま、人が確定した単一額を再現する内部記録。選択帯かoverrideか、確定者・時刻・理由、条件の受諾状態をquote版に結び付ける。未確認値はnullとし0にしない。人確定額がnullまたは条件承認がpendingなら請求書を生成せず、概算幅の見積表示だけにする。確定額と各幅の同一シナリオ値は整合を検査し、⑪は合算・再計算せず、差異時は④の新しいquote版と再確認を求める。見積幅を請求額に転記しない。

### 法制度（架空デモ値とは区別）
国税庁による適格請求書の記載事項は、交付先、売手名と登録番号、取引年月日、取引内容、税率ごとの対価額と適用税率、税率ごとの消費税額等。登録番号は発行事業者登録後に通知される。登録状態が不明なら適格請求書発行事業者と表示しない。デモ番号は必ずサンプル表示。国税庁資料では消費税額等の端数処理は一の適格請求書につき税率ごとに一回で、端数方法は切上げ・切捨て・四捨五入等から選ぶ。各明細行で丸めて合算しない。税区分・正式運用は工場・税理士に確認する。

- [国税庁「インボイス制度について」](https://www.nta.go.jp/taxes/shiraberu/zeimokubetsu/shohi/keigenzeiritsu/invoice_about.htm)
- [国税庁「適格請求書に記載する消費税額等の端数処理」](https://www.nta.go.jp/taxes/shiraberu/zeimokubetsu/shohi/keigenzeiritsu/pdf/0017007-067_15.pdf)

金額・タップ数・案の時間・評価点・デモ値はすべて架空の設計想定で、相場・実測・法的適合・開発保証ではない。制度説明のみ国税庁一次情報に基づく。契約データ転載、自動API取得、スクレイピングは前提にしない。

## 5. 推奨MVP3案と接続

### 推奨：D01 + D08 + D23
6時間デモの架空配分はD01 1.0h + D08 1.5h + D23 1.5h = 4h、残り約2hを既存フロー・Simulator・操作確認に充てる。実測ではない。PDFライブラリ、日本語フォント、会計CSV、API、実送信は複雑なためmockまたはブラウザ表示にする。
1. D01で④の確定後にスマホ帳票を提示。
2. D08で概算幅とS20条件・連絡条件を分離。
3. D23で当時の入力と帳票を固定・再表示。

    ① labor（人時幅・工程・理由） ─┐
    ③ labor_rate（単価・適用日） ──┼→ ④ quote（明細・幅・根拠・確定者）
    ⑤ items（材料・価格時点） ────┘                 ↓
                                             ⑪型検査→D08+D01
                                                       ↓
                                                    D23保存

①の実作業人時を保持し、④が承認済み非請求工程だけ除外してH_job_billable幅と単価からquote金額を算出する。非請求理由・承認者をquote理由に保ち、⑪は再計算・再丸めや除外工程復活をしない。③単価と適用日は当時値、⑤部品・材料は工賃と別行・価格種別・更新日を保持。④quoteは{lines,subtotal,tax,total:{low,typical,high},reasons,confirmed_by,override_reason}。幅を保つためsubtotal/taxもMoneyRangeにする差分を④担当と合意。内部approval snapshotはquote_version・単一のconfirmed_amount（subtotal/tax/total）・選択帯またはoverride・確定者/時刻・override理由・condition_acceptanceを保持する。幅を残したまま人確定額を再現するための記録であり、未確定nullでは請求書を生成せず幅つき概算見積だけを表示する。見積幅は請求額に転記しない。登録状態不明なら適格請求書と名乗らず、デモ番号はサンプル表示。匿名ID、snapshotを保存。音声保存なし、共有mockのみ。

### 6時間デモ手順
1. Simulatorで車両・作業・条件を選ぶ。
2. ④から架空の工賃・部品・税・合計幅を受け、実価格でないと表示。
3. 人が必要な場合は帯選択またはoverrideで単一額を確定し、幅はそのまま保持。確定額nullなら請求書化をしない。
4. D08で架空の追加条件と作業前連絡を確認。
5. D01でスマホ帳票を提示。
6. D23で保存し同じsnapshotを再表示。
