# 1日MVP設計

事業者の仕事を一つ改善し、その変化を発表で示せる最小の開発範囲を決める。ユーザーが選んだテーマや既存の実装を尊重する。

## 入力

課題IDと根拠、チームの選択、データの提供状況、開発環境、現在時刻と残り時間、3人の得意分野。ヒアリング結果がなくても共有メモから暫定案を作り、仮説と明記する。

## 手順

1. 「誰が、どの場面で、何を入力すると、何が得られ、次にどう行動するか」を一文にする。複数の課題が混じる場合、効果を見せられる最小の流れを推薦する。利用者の指定した範囲を勝手に変更しない。
2. 候補が複数ある場合、課題の根拠、データの入手性、実装時間、実演の分かりやすさで比較する。根拠のない点数で順位を確定しない。推薦とチームの決定を分ける。
3. 入力項目、出力項目、必須の処理、失敗時の振る舞いを定める。計算・集計・記録整形・AI生成を区別し、AIの出力を人が確認する箇所を決める。
4. Googleの基盤を使用する予定であることを前提に、具体的なサービス、利用可能なアカウント、API、実行・公開方法を確認する。未確認のサービスを採用決定にしない。決定が必要な点を残し、環境に依存しない画面・データ・処理仕様を先に進める。
5. 当日必要な機能と、PoC以降の候補を分ける。連携が未確認なら、許可されたCSVや手入力で中心の流れを実演できるか検討する。実データの代わりに例示データを使う場合は、画面と発表で区別する。
6. チームの3人に、画面、処理・データ、ヒアリング・検証・発表などの担当を割り当てる。名前が不明なら担当枠で示す。兼務と接続部分の担当、統合確認の時刻を決める。この分担は人間の担当案であり、AIサブエージェントの起動指示ではない。
7. 残り時間から逆算する。説明メモでは16:00に発表開始。暫定目安は14:30に機能追加を終え、15:00に実演を確認、15:30に発表練習。当日の案内・現在時刻・進捗に合わせて変更し、準備時間を確保する。開催日と集合場所は説明メモでは未確認。
8. 正常入力と、その課題で起こりやすい失敗入力で受入条件を作る。効果の測り方を定め、実測・計算上の推計・今後の期待を分ける。

## 成果物

一つのMVP仕様として次を返す。

- 選択した課題ID、根拠、利用者と改善する作業。
- 入力、処理、出力、利用者の次の行動。
- 当日実装する範囲とPoC候補。
- 環境・データの確認状況、依存する未確認事項。
- 担当、接続部分の仕様、統合・検証・発表準備の時刻。
- デモ用の入力と期待結果、受入条件、効果の測定方法。
- データやAPIが利用できない場合の縮小案と、縮小しても示せる価値。

## 完了条件と引き継ぎ

チームが開発を始められる粒度で、中心の操作、担当、受入条件、残る依存関係が分かること。チーム未承認の仕様は推薦案として報告する。

実装開始時はリポジトリのGit協業手順を使う。データ処理が必要なら課題IDとデータ仕様を分析工程へ、画面と処理の仕様を試作工程へ渡す。
