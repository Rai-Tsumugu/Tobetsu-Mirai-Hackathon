# 30案の演算アルゴリズム：共通仕様

[system-ideas-30.md](../../docs/man-hours/system-ideas-30.md) の S01〜S30 を、同じ入力（[scenario.json](scenario.json)）で計算して比べるための共通仕様。数値はすべて架空値で、補正率・人時の実測ではない。

## ファイル

| ファイル | 内容 |
|---|---|
| `scenario.json` | 全案共通の入力（車両、作業、現車状態、実績、暫定値、工場方針） |
| `sNN_<英語スラッグ>.py` | 案ごとのアルゴリズム。Python 3 標準ライブラリのみ |
| `results/SNN.json` | 各スクリプトの出力 |
| `build_table.py` | `results/*.json` から比較表 `README.md` を作る |

実行: `python3 src/30-algorithm/sNN_xxx.py`（標準出力に JSON を出し、`results/SNN.json` にも書く）。

## 共通ルール

1. **入力は `scenario.json` からだけ読む**。スクリプト内に数値を直書きしない。シナリオにない値が必要なら `assumptions` に「仮定」として明記する。
2. **出発点は重複控除後の基準 1.7 人時**（`base_totals.deduplicated_base`）。S17 だけは 2.0 から控除を自ら計算する。
3. **その案が扱う要因だけを反映する**。他案の要因（例: S07 での固着対応）は加えない。比較表で各案の寄与が分かるようにするため。
4. **未確認を 0 として確定しない**。typical に入れないなら high（上限）側に入れ、`unknowns` に記録する。
5. **地域・年式・走行距離だけで工数を増やさない**。加算は観察した状態と追加工程に対応づける。
6. **人時と経過時間を分ける**。待機（融解・浸透・乾燥・部品待ち）は経過時間にだけ入れる。
7. **暖房費・家賃・材料費は人時に足さない**。金額は `other_outputs` に出す。
8. **3方式を平均しない**（S30）。
9. 人時は丸めずに計算し、出力時だけ小数第2位に丸める。
10. 工数を算出しない案（例: S04、S21、S27、S28）は、`labor_hours` に基準 1.7 を据え置き、`result.note` に「工数は変えない」理由を書く。

## 解釈の統一（第2版、2026-10-11）

第1版のルール3（他案の要因を混ぜない）とルール4（未確認は high に入れる）がぶつかり、案ごとに解釈が割れた。比較の前提をそろえるため、次のとおり決める。ここに書いた解釈が第1版の該当ルールより優先する。

- **U1 案の範囲**: 「その案が扱う要因」は、[system-ideas-30.md](../../docs/man-hours/system-ideas-30.md) §3 の「主に扱う要因」列と、§4 の「仕組み」に書かれた工程とする。
- **U2 low / typical / high の意味**
  - typical: その案の範囲で、観察済みの状態から見込む値
  - high: その案の範囲での上限。観察済みの悪化シナリオと、**範囲内の未確認項目の上限**を含める
  - 範囲外の未確認項目は `unknowns` に記録するだけでよい。note に「high は上限ではない」とは書かず、「この案の範囲での上限」と書く
  - S04・S21・S24 は、docs の仕組みが「未確認を上限の幅に反映する」ことなので、未確認項目に暫定値（`mechanic_provisional_add_ops` の high）を当てて high に入れてよい
- **U3 締結部の扱い**（S01・S03・S09・S11〜S16・S19〜S21・S25・S29・S30 など締結部を扱う案）

  | 錆の観察 | low | typical | high |
  |---|---|---|---|
  | 中（固着対応の可能性） | 0 | FX-SEIZE typical | FX-SEIZE high |
  | 重（折れ込みの可能性） | FX-SEIZE low | FX-SEIZE typical | FX-SEIZE high ＋ FX-BROKEN high ＋ FX-THREAD high |
  | 未確認 | 0 | 0 | FX-SEIZE high |
  | 軽 | 0 | 0 | 0 |

  折れ込みは、固着対応を試みたあとに起きる別工程として足す（二重計上ではない）。実績から単価を作る案（S11〜S14）は FX-* の暫定値を自分の単価に置き換えてよいが、表の割り当ては変えない。
- **U4 サブフレーム**: J1・J2 では外さないので作業範囲外とする。high には入れず、`unknowns` に「腐食があれば作業範囲の拡大（AG04）として見積もりを変更し、顧客の了承を得る」と書く。
- **U5 経過時間の待機**: その範囲で FX-SEIZE を含めたら浸透待ち 0.25、FX-HUBCLEAN を含めたら防錆乾燥 0.3（冬季仮説値）、氷塊除去を含めたら融解待ち 0.5 を、該当する low / typical / high それぞれの経過時間に足す。待機は人時に入れない。
- **U6 タイヤ重量**: 共通基準 1.7 は1人運搬（18kg以下）を前提とする。23kg による差（＋0.08人時）は S07 だけが扱う。他の案はこの差を指摘・加算しない。
- **U7 人時の定義**: `labor_hours` は実作業人時とする。請求しない作業（下回り洗浄）も、その案の範囲なら人時に入れ、請求人時は `other_outputs` に別に出す。
- **U8 付随部品**: `companion_parts_catalog_S22` の表示しきい値（0.15）未満の候補（パッドセンサー、ブレーキホース）は high に入れず、`other_outputs` に参考として出す。
- **U9 工数を算出しない案**（S10・S26・S27・S28）は low = typical = high = 1.7 とする。S10 の区分別の差を人時に足すと、季節・年式による一律加算になるため。

## 出力 JSON

```json
{
  "id": "S01",
  "name": "状態チェックリスト加算型",
  "base_method": "A",
  "factors": ["HK01", "AG01", "AG02"],
  "algorithm": ["手順1: …", "手順2: …"],
  "inputs": [{"key": "condition.fasteners", "value": "…", "status": "確認済み|申告|仮定|不明"}],
  "intermediates": [{"label": "固着対応の可能性がある締結部", "value": 2, "unit": "本", "formula": "…"}],
  "result": {
    "labor_hours": {"low": 1.7, "typical": 2.0, "high": 2.6},
    "elapsed_hours": {"low": 1.9, "typical": 2.3, "high": 3.0},
    "other_outputs": [{"label": "時間単価", "value": 8000, "unit": "円/人時"}],
    "note": "…"
  },
  "assumptions": ["…"],
  "unknowns": ["…"]
}
```

- `elapsed_hours` は、待機や2人作業を扱わない案では `null` でよい。
- `intermediates` は表に載せる「重要な途中計算数値」。3〜8項目。各項目に `formula`（式）を書く。
