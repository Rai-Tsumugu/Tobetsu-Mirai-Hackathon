# 統合版 工数見積もりエンジン（決定版）

[30案](../../../docs/man-hours/system-ideas-30.md)の比較から、良いところを1本の流れにまとめた見積もりエンジン。入力の数値は架空値で、補正率や人時の実測ではない。計算結果は提案で、確定は整備士・見積もり担当者が行う。

```bash
python3 src/30-algorithm/integrated/estimator.py          # result_example.json / .md を出力
python3 -m unittest discover -s src/30-algorithm/integrated -p "test_*.py"
```

## 1. 値の置き場所

コード（`estimator.py`）は数値リテラルを1つも持たない。テスト `test_engine_has_no_numeric_literals` と `test_engine_has_no_numbers_hidden_in_strings` が構文木を走査して検査する。数値はすべて、次の変数ファイルか `constants.py` の名前付き定数から来る。

| 種類 | ファイル | 中身 | 変わるきっかけ |
|---|---|---|---|
| 変数: 過去の実績 | [data/records.json](data/records.json) | 実績（見積もり・実作業人時・原因タグ）、工程ログ、同一車両の履歴、他工場の匿名実績 | 作業が終わるたびに追加される |
| 変数: 最新の情報・工場方針 | [data/shop_params.json](data/shop_params.json) | 整備士の暫定値（v1）と請求するか否か、採用する補正表の版と更新規則、状態ごとの分岐、締結部の割り当て、しきい値、待機時間、加点表、経費と単価に含める経費、材料単価、丸め方 | 整備士の見直し、経費・材料の値上がり、方針の変更 |
| 変数: 基準工数 | [data/job_catalog.json](data/job_catalog.json) | 作業ごとの基準人時、含まれる工程、作業部位 | 基準データの版の更新 |
| 入力: 今回の見積もり | [data/case_example.json](data/case_example.json) | 電子車検証、車両、入庫時の観察、写真、気象予報、音声メモ | 見積もりごと |
| 定数 | [constants.py](constants.py) | 和暦の起点、月数、丸め桁、状態の選択肢、季節・方式の名前 | 定義なので変わらない |

### 実績で変わる値の流れ

`records.json` の原因タグから1単位あたりの人時を集め、件数が `rate_update_rule.min_records` 以上の工程だけ、`rate_update_rule` に書いた統計量（low=最小、typical=中央値、high=最大）で補正表の候補（v2）を作る。候補は自動では使わない。整備士が承認したら `shop_params.adopted_rate_table` を `"v2"` に書き換える（S12）。方式Bの類似実績（S08）も同じ実績から毎回計算する。同一車両の前回実績は、車の状態が変わっているので集計に入れず別に示す（S09）。比較条件が相違する実績を除外するかは `similar_case.exclude_if_differs` で決める。

### 定数に置いたもの・置かなかったもの

- 定数にしたもの: 和暦の元年（令和 2019、平成 1989、昭和 1926）、1年=12か月、「1単位」「1回だけ計上」、状態の選択肢の名前、出力 JSON の字下げ幅
- 変数にしたもの: 冬季の月、確認強度・気象・連絡のしきい値、加点表、待機時間（冬季の値を含む）、タイヤの基準の前提重量（job_catalog）と1人で扱える重量（shop_params）、重量の確認状態の読み替え、人時と円の丸め桁・丸め方。いずれも工場の判断や観測で変わりうる
- 読み込み時に検査するもの: 状態の選択肢が constants と shop_params で一致すること、冬季と冬季以外の請求人時の合計が年間と一致すること、単価の配賦方法が既知の値であること

## 2. 処理の流れと取り込んだ案

| 段階 | 内容 | 取り込んだ案 |
|---|---|---|
| 1. 車両情報 | 電子車検証の和暦を西暦に直し、初度登録からの経過年数と季節を出す。使用者の情報は取り込まない | S26 |
| 2. 基準工数 | 選んだ作業の基準人時を合計し、共通工程（リフト・前2輪脱着）を1回分にする。前処理は入庫1回だけ | S17 |
| 3. 工程の展開 | 状態ごとの分岐（`condition_rules`）で工程を足す。雪・氷・下回り洗浄、ハブの錆、ローター固着、ブーツ | S01, S02, S05, S15, S22 |
| 〃 | 締結部1本ずつ、錆の区分で固着対応・折れ込み・ねじ山修正を割り当てる（`fastener_treatment`） | S03 |
| 〃 | タイヤ重量が1人の上限を超えたら、2人作業（または機材）の差分を足す | S07 |
| 4. 単価 | 承認済みの補正表（v1）を使い、実績から v2 候補を作る。他工場の値は参照幅だけ | S11, S12, S13 |
| 5. 3点見積もり | low（少ない）／typical（観察から見込む）／high（未確認と折れ込みを含む上限）。待機は経過時間にだけ足す | S18, S19 |
| 6. 方式比較 | 方式A/Cの積み上げと、方式Bの類似実績を並べる。平均しない | S08, S30 |
| 7. 確認 | 確認強度、気象による前処理の確認、未確認の確認リスト（上限への影響が大きい順）、確認優先度、撮影の漏れ、AIと整備士の判定の一致、同一車両の前回との差 | S04, S06, S09, S16, S21, S23, S24 |
| 8. 金額・説明 | 発生した場合だけの追加と作業前連絡の要否、時間単価（年間配賦・冬季配賦）、材料費の別建て、顧客向けの内訳 | S20, S27, S28, S29 |
| 9. 記録の分析 | 見積もりと実績の差（季節×年数区分）、工程ログの集計、音声メモの原因タグ振り分け | S10, S14, S25 |

### 30案から決定版にするときに決めたこと

- **確認優先度（S21）は人時の幅を変えない**。docs は「上限の幅」にも使うとしているが、比較では年数・走行距離で上限が 3.9→8.5 人時に動く問題が出た。決定版では未確認と折れ込みは常に high に入れ、スコアは確認の順番と時期にだけ使う。
- **差分ログ（S10）・音声メモ（S25）・他工場の実績（S13）は見積もりに直接足さない**。差分ログは区分で一律に足すことになり、音声メモと他工場の値は確認前の候補だから。v2 候補（S12）を通して、承認後に反映する。
- **タイヤ重量が仮定値のとき（S07）は、2人作業の差分を typical と high にだけ入れる**（`state_treatment` の「仮定」）。
- **AIの判定（S23）は計算に使わない**。整備士の確定値だけを使い、一致率を表示する。
- **サブフレームなど作業で外さない部位**は high にも入れず、作業範囲を広げるときは見積もりを変更すると記録する。

## 3. 例の結果（data/ の架空値）

| 区分 | low | typical | high |
|---|---|---|---|
| 人時（A/C: 基準＋状態に応じた工程の積み上げ） | 2.35 | 3.24 | 10.53 |
| 請求人時（請求しない下回り洗浄を除く） | 2.20 | 3.04 | 10.23 |
| 経過時間（待機 1.05 時間を含む） | 3.40 | 4.27 | 11.56 |
| 人時（B: 類似実績3件。同一車両の前回は別に表示） | 2.30 | 2.40 | 3.00 |
| 工賃（請求人時 × 年間配賦 8,000 円/人時） | 17,600 | 24,320 | 81,840 |
| 材料費（円、四捨五入） | 1,869 | 2,125 | 9,137 |

typical の 3.24 は 30案の中で最も大きい S16（3.16）と同程度で、各案が別々に見ていた要因（前処理、固着、ハブ、ブーツ、タイヤ重量）を重複なく足し合わせた値になっている。high と typical の差 7.29 人時のうち 6.5 人時は「発生した場合だけの追加」として見積書に別記する。そのうち 6.3 人時（左ブラケットボルトの折れ込み 4.3、見えないスライドボルト 1.2、ローター固着 0.8）は、連絡基準（0.5 人時または 5,000 円）を超えるので作業前に連絡する。詳細は [result_example.md](result_example.md) と [result_example.json](result_example.json)。

## 4. 検証

Haiku 3体が独立に検証した（変数・マジックナンバーの監査、data/ からの算術の再計算、ガードレールと30案の取り込み）。算術は全項目が一致した。指摘を受けて、請求しない工程を工賃から除く、同一車両の前回実績を方式Bの集計から外す、作業部位に未確認があれば上限に入れる、タイヤ重量の確認状態としきい値を変数にする、丸め方と補正表の更新規則を変数にする、ラベル・部位名を data に移す、の修正をした。修正内容はテスト（28件）で固定している。

残した判断事項: ハブ当たり面の錆落とし（FX-HUBCLEAN）と基準のパッド交換に含まれる「清掃」が重なるか、ローター固着除去と同じ high に入れてよいかは、整備士に確認する。方式Aと方式Cは決定版では同じ工程の積み上げになるため、比較画面（S30）は A/C と B の2列にしている。
